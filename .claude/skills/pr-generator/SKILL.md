# PR Generator (cal.diy only)

This skill is scoped exclusively to the **cal.diy** repository. Do not reuse it for other projects.

## When to use

Whenever the user asks to open, create, or draft a Pull Request for changes in this repository (e.g. "abre um PR", "cria o PR dessa branch", "open a PR").

## Required PR structure

Every PR description generated by this skill MUST contain the following four sections, in this order:

1. **Description** — A clear and objective explanation of what the PR changes. No vague language; state exactly what was added, fixed, or removed.
2. **Why** — The motivation/reason for the change (bug fix, feature request, tech debt, incident follow-up, etc.). Explain the "why", not just the "what".
3. **How to test** — Concrete, reproducible steps or examples a reviewer can follow to verify the change (commands to run, pages/flows to click through, edge cases to check). Prefer copy-pasteable commands when applicable.
4. **Impact** — What parts of the codebase/product are affected, potential risks, side effects, and anything reviewers or on-call should watch for after merge.

## Workflow

1. Confirm the current branch is not `main` and has commits ahead of `main`. If the branch is not pushed yet, note that it will need to be pushed before opening the PR.
2. Inspect the changes: run `git log` and `git diff` against `main` (or the PR base) to understand everything included — not just the latest commit.
3. Draft a PR title: short, imperative mood, under ~70 characters.
4. Draft the PR body in Markdown using the four required sections above.
5. Show the drafted title and body to the user and ask for confirmation or edits. Never open the PR without explicit approval.
6. Once approved, push the branch if needed and create the PR with `gh pr create --title "..." --body "..."` (use a heredoc for the body to preserve formatting).
7. Return the PR URL to the user.

## Constraints

- Never skip any of the four required sections.
- Never push branches or open PRs without explicit user confirmation.
- Never force-push or rewrite history as part of this skill.
- Keep the tone factual and concise — no marketing language, no emojis unless the user asks.
